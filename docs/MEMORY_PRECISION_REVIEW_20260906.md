# 记忆精度专项审查与设计

> 定位：2026-09-06 的精度审查与设计来源，保留当时的实验和问题；历史复现不表示问题仍未修或新接口已经验收。现行设计看[Memory 设计目录](./README.md)、[记忆主稿](../../astrbot_plugin_private_companion/docs/MEMORY_CONTRACT_V0.md)及[查询专题](../../astrbot_plugin_private_companion/docs/MEMORY_QUERY_SESSION_DESIGN_V0.md)，当前证据看[路线](../../astrbot_plugin_private_companion/docs/FRAMEWORK_ROADMAP_AND_STATUS_V1.md)。

日期：2026-09-06。源码基线：`a12c386`（2.0.0）。

本次审查针对“记得多但记不清”，检查采集、摘要、事实更新、候选召回、最终注入、证据保留与评测。只增加离线复现脚本和设计文档，未修改生产逻辑、配置或真实记忆数据。以下合成案例证明具体路径存在问题，不代表这些问题在全部用户中的发生率；没有用生产聊天日志推断比例。

## 1. 结论

现有系统已经具备核心记忆、Memory Atom v2、分槽、多路召回、RRF/MMR、可选 Embedding/Rerank、来源引用、ACL、纠正反馈与主动重建。主要缺口是这些能力之间仍以“整条记忆”作为检索和统计单位，而用户需要的是某个对象在特定时间、条件下的准确细节。

已经复现六类问题：不同事实被错误合并；错误事实通过词语重合校验；命中记录但答案未进入提示词；全库候选限额挤占当前用户的向量召回；摘要引用的原始证据被清理；MRR 漏算未命中的问题。另有注入强化的反馈偏差需要观测，不能直接认定为错误事实来源。

首期目标应改为：能够说明“谁、什么对象、哪一项、当时还是现在、确定程度、依据在哪里”，并在证据不足时准确表达缺失。增加 top_k、上下文字数或模型调用次数不能替代上述语义。

## 2. 已复现问题

### M-01 不同属性被当作同一可变事实覆盖（P1）

位置：`core/retrieval.py:1090` `_collapse_mutable_fact_results`、`:1165` `_mutable_fact_keys`；分槽结果在 `:390` 调用折叠。

代码按 password/account/phone/email/address/name 等词语类别分组，在同一所有者与主体下只保留最新记录，没有区分家庭地址和公司地址等属性，也没有要求真实的 supersedes 关系。它发生在 top_k/分槽选择后，被删掉的记录不会在这个步骤补回。

复现：同一用户的家庭地址较旧、公司地址较新，询问两者分别是什么；结果只剩公司地址，家庭地址被标为 `mutable_fact_latest_only:key=address`。这是检索阶段丢失，不是原记录被删除。历史查询同样需要区分有效时间，不能默认“最新即答案”。

设计：用主体、具体属性、限定条件、有效时间和明确修订关系处理更新。只有同一断言槽且有替换依据时才折叠，历史有效值继续支持过去时查询；无法判断的冲突保留并向模型说明。不继续增加地址/名字关键词特判。

### M-02 词语重合不能证明事实被原文支持（P1）

位置：`core/summarizer.py:514` `fact_supported_by_rows`；`:168` `summary_quality`；`core/service.py:4743`。

当前校验接受原文包含断言，或至少两个非通用词语命中。它能检查粗略相关性，不能确认否定、人物角色、日期、数值或条件是否一致。通过后的摘要可进入 stable_memory，默认 confidence 为 0.72；summary/canonical 并没有逐句进行相同语义验证。

两例均被当前检查判为支持：

| 原始证据 | 错误断言 |
| --- | --- |
| 小林不喜欢香菜 | 小林喜欢香菜 |
| 小林预约周三下午三点看牙医 | 小林预约周五下午五点看牙医 |

设计：词语重合仅作为相关性提示。抽取提示词保留否定、主客体、条件和绝对时间，并返回逐断言证据片段。结构层验证引用存在、主体与作用域；有纠正、矛盾或高后果事实时按需进行语义复核，不能用词语命中数冒充事实确认。普通低置信度内容保持候选或不确定表达，避免每条聊天新增同步模型调用。

### M-03 命中记录不等于答案进入上下文（P1）

位置：`core/injection.py:373`、`:435` `_memory_item_line`；`core/retrieval.py:312` 的固定分槽次序。

注入将 `key_facts` 按存储顺序拼接，优先于 canonical/content，然后按单条字数预算从头截取；默认 `max_item_chars=220`。这一层未根据当前问题选择事实。前面的事实即使与问题无关，也会占掉后面答案的位置。按记忆 ID 记录“已注入”无法揭示这个损失。

复现：四项事实，前三项是资料整理背景，第四项是蓝色文件夹的具体位置。整条记忆已选中且 ID 进入 included_memory_ids；即使总预算扩大到 6000 字，默认单条上限仍截掉第四项，最终上下文没有答案。前三项使用合成占位内容，此例验证截断机制，不评估真实主题频率。

设计：在记录内选择与查询相关的断言/证据片段，先满足答案需要，再补关系与氛围；每个事实保持完整语义，不能仅对长段前缀截断。总预算不足时先减少无关条目。记录 selected_memory_ids 之外，还需记录 selected_assertion_ids、实际注入片段及省略原因。重建工具可以补证，但普通细节问题不应完全依赖模型主动发现截断。

固定分槽次序可能进一步让关系/自我背景挤占细节预算，这是待采样评估的放大因素，本次不把它单列为已证实的用户级故障。

### M-04 向量候选在权限过滤前被全库限量（P1）

位置：`core/store.py:11350` `_list_embedding_candidate_rows_sync`、`:11383`；`core/retrieval.py:1578`、`:1640`；后续 `_rank_candidates_sync` 才做可见性校验。

有两次提前截断：先按全库 importance/时间取有限向量行（默认 1200），再按相似度保留全库 top_k（默认 32）。这两个阶段没有当前调用的 Scope/ACL。最终过滤仍会挡住不可见记忆，本问题是候选被挤占，不是已经发生隐私泄露。

复现：当前用户有一条可见且相关的记录，另一用户有 33 条相似度略高的私聊记录。向量 top32 全部来自另一用户，后续可见性过滤后为 0，当前用户的目标单独校验则可见。另用上限 2 的缩小案例证明低 importance 目标在相似度计算前就被排除；后者验证限额顺序，不声称默认上限是 2。其他词法/当前窗口路线可能补回目标，因此不能把单条向量路线丢失等同于全系统必然无结果。

设计：先限定合法可见候选空间，再做有界语义 top_k；复杂 ACL 可由粗粒度命名空间预筛加受限分页补取实现，最终仍重验权限。按规模决定是否需要向量索引，避免固定的全库 importance 前缀成为语义搜索边界。增加其他用户的无权记录不应降低当前用户的目标召回率。

### M-05 长期摘要仍在，但证据已不可解析（P1）

位置：`core/service.py:6881` `_run_raw_event_retention`；`core/store.py:11133` `_prune_retained_rows_sync`；`core/service.py:6239` `_navigate_event_records`、`:6410` `_serialize_navigation_evidence`。

已总结的普通时间线默认在 30 天后清理；SQL 根据 summarized_at、时间和非 historical_archive 分类删除，没有检查仍有效摘要的 key_facts_with_refs。historical_archive 与未总结记录有保留保护，不能把问题扩大为“全部历史被删”。

复现：保存引用一个原始事件的有效长期摘要，标记该事件已总结，再按过期时间执行清理；摘要仍在，但其引用查不到原事件。当前 event_context 主要展开 memory record 的 content/evidence/canonical，并不据 key_facts_with_refs 自动还原被引用的原始消息。摘要中未保留的细节因此难以补回。

设计：长期有效断言保留最小可解释证据片段、消息 ID、主体和时间，独立于整段聊天日志的保留期。清理前检查证据是否已有授权的压缩副本或仍可解析；不需要无限保留全部聊天。用户删除/撤回时同时清除该证据和派生事实，索引不能作为绕过删除的副本。已丢失的证据标记 source_missing，不凭旧摘要补造原文。

### M-07 评测遗漏未命中的零分（P2）

位置：`benchmarks/run_recall_evaluation.py:135`、`:160`。

只有命中时才把倒数排名加入列表，MRR 使用该列表的平均值。完全没有命中的问题被从分母中移除。

复现：两个问题，一个首位命中、一个完全漏召回，正确 MRR 应为 0.5，现有脚本输出 1.0；Recall 同时为 0.5。故不能用当前 MRR 宣称召回精度已经很好。

此外，此脚本只检查 memory ID 的排名，未经过生产分槽、事实片段选择、最终注入与答案支持验证。先修正指标口径，再补整链路评测；现有 ID 召回评测继续作为候选阶段指标保留。

## 3. 需要观测的反馈风险

M-06：`core/store.py:11532` 每次真正注入后把 reinforcement_score 增加 0.025；`core/memory_lifecycle.py:148` 将其作为最高 0.12 的排序加分，维护侧也使用强化值判断保留。

复现证实一次注入、没有用户确认时强化值变为 0.025。这是已有复述强化机制，不会直接把 confidence 改为“用户确认”，也不证明它单独造成错误记忆。不过，“先被选中 -> 被强化 -> 更容易再次入选”会偏向重复暴露的内容，应单独观察。

设计：区分曝光次数、模型实际使用、用户明确确认、纠正和独立来源佐证。可以保留有上限的熟悉度效应，但不把曝光当真实性或独立证据。对事实正确性的学习只依赖可归因反馈；不得因用户沉默而认为答对。

## 4. 首期记忆契约

在现有 MemoryRecord 上渐进增加断言层，兼容旧记录，不新建第二套记忆运行时：

| 对象 | 最小语义 | 所有者 |
| --- | --- | --- |
| EvidenceRef / EvidenceExcerpt | 原始消息/工具回执引用、最小片段、主体、时间、权限、保留状态 | 来源域拥有原始数据，记忆拥有获授权的必要证据片段 |
| MemoryAssertion | subject、predicate、value、polarity、qualifiers、valid_from/to、asserted_at、来源及修订关系 | 记忆服务；外部领域仍保有自己的事实权威 |
| EpisodeSummary | 一段经历的可读摘要及 assertion_refs，明确这是损失性摘要 | 记忆服务 |
| MemoryView | 当前查询下有权限的有效值/历史值、冲突和证据缺口 | 记忆服务的临时投影 |
| AnswerEvidence | 最终用于回答的断言、完整证据片段、时态、置信与缺失原因 | 记忆生成，核心上下文编排消费 |

断言粒度必须能区分家庭地址与公司地址、用户偏好与第三方转述、过去计划与实际完成。未知主客体不推断成当前用户；昵称用于展示，稳定 ID 用于归属。现有 profile 单值事实与 supersedes 能力应复用，不能因为本次发现就认定项目完全没有纠正/替换机制。

`MemoryMutation` 的可变事实更新携带原断言/预期 revision、证据和更新语义：新增、纠正、更改生效时间、撤回。事务检查和引用约束负责数据一致性；语义归因优先由抽取提示词和已有模型结果完成，歧义保留为冲突候选。

原生联动分工：日历拥有安排与完成回执，创作拥有作品版本，一起/游戏/直播拥有各自会话事件，现实/屏幕拥有观测；记忆保存带来源的经历和断言，向核心提供答案证据。模型重复描述、角色模拟和用户陈述不能变成三个独立事实来源。

## 5. 提示词与检索编排

抽取提示词应先服务事实完整性，再生成可读回忆：

```text
逐项提取将来可能需要准确回答的事实。每项保留主体、具体对象/属性、
值、肯定或否定、时间、条件和支持它的原始事件及短片段。
区分用户本人的事实、第三方转述、角色模拟、意图与已完成行为。
纠正只作用于有依据的同一断言；不同属性或不同有效时间不要互相覆盖。
先输出有证据的独立断言，再生成引用这些断言的可读摘要。
无法确定时标注缺失或冲突，不把猜测写成事实，不为凑数量重复提炼。
```

查询编排优先明确当前问题的主体、属性、时间与所需细节；省略指代只使用相关的当前对话或显式回复链解析，不把全部陪伴背景拼入检索词。公开版本化的 RecallRequest 传递这些查询线索和预算，不能靠私有事件属性传递。

```text
先用本轮 AnswerEvidence 回答当前问题，保留对象、否定、时间、单位和条件。
关系与氛围只能影响表达，不能补出答案证据中缺失的细节。
历史值与当前值同时存在时按问题时态选择；仍有冲突时说明冲突。
证据不足时，只围绕缺失项进行有界补检索或自然确认。
若来源已经丢失，不声称记得原话，也不把流畅摘要当作精确记录。
```

检索采用“可见空间 -> 多路候选 -> 相关断言/片段 -> 有效时间与冲突解析 -> 答案证据优先 -> 最终注入”。Rerank/MMR 和分槽继续复用，但评价单位同时包含断言，不用平均分配条数代替答案完整性。资源预算限制总开销，普通精确问题不必每次进入多步重建。

## 6. 实施顺序与验收

1. 校准评测：修正 MRR，把本文合成反例加入质量基线；按用户授权采集脱敏失败样本，记录插件版本、有效配置、Provider 与每阶段省略原因。
2. 优先修复有明确影响的读取问题：保留不同属性/历史断言，按问题挑选完整事实片段，区分命中与实际注入；验证不破坏 ACL 和当前状态保护。
3. 调整写入与证据契约：提示词抽取断言、按需复核、修订/撤回、证据保留与来源缺失状态；旧数据先只读投影，不批量凭摘要补造证据。
4. 调整候选空间：权限预筛、有界补取、必要时索引，验证新增无权数据不会挤占合法召回；不直接放大全库扫描上限。
5. 与原生 N-01--N-04 场景共同验证，影子对照后按用途切换；曝光强化的调整根据真实反馈和精度评测决定。

| 验收问题 | 检查标准 |
| --- | --- |
| 旧值、新值、纠正与历史查询 | 正确返回问句所需的有效时间版本，不把不同属性当作冲突 |
| 否定、人物归属、日期、数量/单位、条件 | 错误断言不能仅凭词语重合通过证据验证 |
| 目标细节位于第一个或最后一个事实 | 在同等预算内保持答案证据可见，不因存储顺序改变结果 |
| 当前用户记录固定，持续增加其他用户数据 | 权限不放宽，合法目标召回率不因其他用户候选挤占而下降 |
| 摘要仍有效但整段日志达到保留期 | 关键断言仍有获授权的证据片段，或明确标记来源丢失 |
| 问题不可回答、来源撤回或事实冲突 | 不把模糊回忆包装为确定答案；不会用关联线索制造事实 |
| 分槽、压缩、生成和补检索 | 分别统计候选 Recall、最终证据覆盖率、断言正确率、无依据细节率及补检索成本 |
| 质量和资源对照 | 记录样本数、P50/P95、Token 与内存；不以条目数量或单一 MRR 代替用户问题解决率 |

其中“最终证据覆盖率”以每个可回答问题所需的 gold assertions 为分母，检查实际注入片段是否覆盖；“断言正确率”以回答中的可核查断言为分母；“不可回答”单独测拒绝无依据断言的能力。标注来自来源材料和人工核对，不能只让同一个生成模型自评。
